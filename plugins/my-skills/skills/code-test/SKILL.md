# 测试与故障诊断

先识别要证明的行为和风险，再选择足够真实、成本最低的验证方式。
沿用仓库测试工具、目录与运行约定；普通需求记录和面试练习不自动加载本技能。

## 场景选择

| 当前任务 | 按需读取 | 要解决的问题 |
| --- | --- | --- |
| Spring 单测、切片或集成测试 | [Spring 专项](references/spring.md) | 测试分层、装配、真实基础设施与环境门禁 |
| 前端组件、交互或浏览器行为 | [前端验证](references/frontend.md) | 组件与浏览器分工、异步和布局的真实性 |
| HTTP 契约、外部协议或吞吐性能 | [接口与性能](references/api-performance.md) | 契约、负载口径、延迟与容量证据 |
| 故障、偶发错误或性能回归 | [诊断循环](references/diagnosis.md) | 复现、缩小范围、验证假设与修复回归 |

场景可以组合，读取与当前风险相关的资料即可；其他技术栈直接沿用仓库已有测试方法。

## 测试选择与质量

- **可观察行为**：从调用方可用的函数、服务、组件或协议接口观察结果，
  选择足以触达风险的最低层级，而不是一律从 HTTP 或 E2E 测起。
- **独立预期**：预期值来自规格、已知样例、独立演算或有依据的参考结果。
  避免复制生产算法计算预期，或只验证同一段逻辑与自身一致。
- **依赖真实性**：业务协作用 stub/mock；事务、锁、协议、浏览器布局等目标保留真实语义。
  验证必要的外部调用契约可以断言参数与条件，不把内部调用顺序当作所有用例的验收条件。
- **验证成本**：纯规则用单测，框架绑定用组件或切片，跨进程契约用集成或 E2E。
  低影响可逆改动可用已有检查、人工观察或静态验证，说明覆盖范围。
- **确定性**：控制时钟、随机种子、异步等待与数据隔离；断言目标行为而不只检查「没有报错」。
  工具故障与业务断言分开解释，不能把未运行或跳过说成测试通过。
- **实现约束**：沿用生产职责和可见性，不为便于测试加入无业务价值的包装或固定外部环境。

## 实施循环

1. **确定行为与基线**
   - 找到现有用例、运行命令、需要证明的结果与外部依赖，先确认相关检查可执行。
   - 适用 TDD 时建立能因目标行为缺失而失败的用例；缺口与环境阻断分别说明。
   - 完成条件：当前行为有独立预期、合适层级和可执行信号，或明确的验证缺口。
2. **小步实现与验证**
   - 每次实现一个行为并运行相关用例，再依据结果选择下一步。
   - 重构保持行为与用例有效，按项目约定进行；不先编写全部假想测试或扩大生产改动。
   - 诊断任务采用专项循环；已有实现可先复现再修复，不强行制造无关失败。
3. **报告证据**
   - 记录命令、实际执行结果、覆盖行为、依赖真实性与未验证部分。
   - 检查测试被框架识别且数量合理；必要时扩大到受影响的集成或回归范围。
   - 完成条件：证据能支持本轮结论；不以单测证明线上配置、视觉展示或最大吞吐量。

已有需求时把用例、层级和证据回填原规格；可用的 `code-spec` 管理验收映射，
`code-review` 核对实现与证据。技能缺失时沿用项目约定，不强制依次调用。
