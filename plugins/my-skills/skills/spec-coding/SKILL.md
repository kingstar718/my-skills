# 需求跟进（Spec Coding）

核心 spec 是需求契约的唯一真相源；唯一真相源不等于所有材料必须放在同一文件。先明确需求和验收，
再实现，最后用证据收敛状态。

## 流程

1. **发现约定**：先读仓库 `AGENTS.md`、需求索引和既有文档结构，沿用已有编号与路径；没有约定时默认
   使用 `docs/project.md` 和 `R-xx`。
2. **登记与选型**：在索引登记一行，并按复杂度选择紧凑模式或目录模式。模板见
   [spec-template.md](assets/spec-template.md)，完整示例见 [spec-example.md](assets/spec-example.md)。
3. **定稿**：写清范围、非目标、可测 AC、关键决策和待确认项；影响实现的待确认项全部闭环后，状态转
   `开发中`，再修改代码。
4. **验证先行**：为每个 AC 选择足以证明行为的最低成本验证层级，先建立失败基线或说明现有缺口，再
   实现到通过。一个 AC 可由多个用例证明，一个用例也可覆盖多个紧密相关的 AC。
5. **实现与收敛**：按验证映射实施，完成后记录最新证据摘要；测试环境通过但尚未发布时保持
   `待回归`，实际发布完成后转 `已上线`。
6. **收尾**：普通需求只更新索引和自身产物。只有长期仓库规则、标准入口或权威文档位置发生变化时，
   才更新 `AGENTS.md`。commit message 引用 spec 路径或编号。

## 产物形态

### 紧凑模式

目标单一、设计直接、验证记录简短时，使用一份 `docs/xxx需求.md`。内容包括状态、范围、AC、关键决策、
任务、待确认项、验证映射和最新结果摘要。

### 目录模式

跨组件、多阶段实施、存在独立架构设计，或执行证据会持续增长时，使用：

```text
docs/specs/R-xx-name/
├── spec.md
├── design.md
└── verification.md
```

- `spec.md`：唯一状态源、范围、AC、关键决策、待确认项、验证映射。
- `design.md`：实现设计、权衡和影响范围，不重复状态与 AC。
- `verification.md`：命令、环境结果、报告链接和未完成验证，不反向定义需求。
- 只有任务需要独立协作或长期跟踪时才增加 `tasks.md`。

不要仅按行数机械拆分。若文档开始混合不同受众、同一内容多处复制，或执行流水账淹没需求契约，就应
拆分并保留单一权威来源。

## 核心 spec 要求

- **状态**：`规划中 / 开发中 / 待回归 / 已上线`，只在核心 spec 维护；索引只展示当前摘要。
- **范围与非目标**：说明这次解决和明确不解决的内容，避免实现扩张。
- **验收标准**：使用可测的 `AC-1/AC-2…`；EARS 句式适合事件型规则，但不是强制文风。
- **输入约束**：涉及输入时，明确格式、数量/长度上限、空值和超限行为。
- **关键决策**：只记录会改变实现或验收的结论与原因，详细方案可链接 `design.md`。
- **待确认项**：区分阻塞项与可采用默认值的非阻塞项；阻塞项未闭环不得进入实现。
- **验证映射**：至少包含 AC、风险/行为、验证层级、用例或证据、基线和当前结果。不是所有 AC 都必须
  落成单元测试。
- **最新结果**：只保留当前结论和证据链接；Git、CI 或独立验证文档承担历史明细。

## 与测试 skill 的边界

本 skill 管理“每个 AC 是否有足够证据”，不规定具体技术栈的测试实现。当项目是 Spring 且任务涉及
测试设计、实现或评审时，如 `spring-testing` 可用，则用它细化单测、切片、集成和 E2E 的选择；不可用时
遵循仓库既有测试约定。两个 skill 独立触发，不要求普通 spec 自动加载测试专项知识。

## 约束

- 小修复是否建 spec 取决于风险、协作和回归面；一行改动不是天然低风险。
- 需求变更先改核心 spec 和对应验证映射，再改代码；Git 历史承担修订记录。
- 多仓库复制需求在核心 spec 记录落点、传播范围和同步状态，避免漏同步。
- 构建与部署步骤放 runbook；`AGENTS.md` 只保留必须遵守的工具链约束、标准入口及链接。
- 不强制创建或复制兼容入口文件；仓库已有 `AGENTS.md`/`CLAUDE.md` 约定时按其单源策略执行。
