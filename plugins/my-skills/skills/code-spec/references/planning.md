# 澄清、调研与任务拆分

仅在信息缺口或工作规模需要时使用对应部分；已明确的小改动按既有约定实施。
当前规则与结论默认写回原需求文档，已有资料用路径或链接引用。

## 按依赖澄清

1. **先查事实**
   - 检查相关调用链、配置、已有规格与用户已提供的信息。
   - 完成条件：区分已核实事实、假设和影响实现的待决策项，不把可查事实交给用户调查。
2. **提出当前可决定的问题**
   - 每个问题只涉及一个决策，附建议、依据与主要影响。
   - 若答案依赖尚未解决的问题，留到后续轮次；独立问题可同轮提出。
   - 完成条件：当前实现范围的必要选择已明确，其余未决项有清晰影响范围。
3. **原位定稿**
   - 更新验收和关键设计，复用已有结论；常规命名和路径选择按项目风格自行处理。
   - 只有真实的业务歧义、范围冲突或不可逆影响需要用户决定，不增加例行确认关卡。

## 业务术语

- 项目已有术语表或接口字段口径时先读取，统一文档与代码命名。
- 一个词指向多个行为时，用具体输入与预期区分，例如「已离港」和「预计到港」不能共用已发生时间。
- 当口头规则与代码不一致，展示实际分支与业务场景，说明待决策的是哪一处口径。
- 术语结论就近记录在原规格或已有术语入口；只有项目确需独立维护时才新增术语表。
  重大取舍沿用既有决策记录，不强制建立 ADR。

## 调研与原型

- **调研**：优先源码、官方文档、协议或第一方接口，给关键结论关联具体来源。
  分开记录已核实事实、推断、未知项及适用版本；资料冲突时说明依据，不用搜索摘要当最终证据。
- **原型**：问题需要运行才能判断时，写清要回答的问题、最小输入与观察信号。
  使用隔离数据和最小可运行样例，标明原型范围；不提前投入无助于决策的工程化。
- **结论**：记录结果及其验证边界，影响需求时回填验收或设计。
  原型不自动成为生产实现；代码保留、清理、提交或发布按任务授权处理。

## 按行为拆任务

- 每项交付一个可独立展示或验证的行为，按需要贯穿相关层，而非固定拆成数据库、后端、前端三批。
- 写清交付结果、对应验收标准、验证方法和真实前置依赖；共享模块不自动构成阻塞。
- 广泛机械迁移可按新增兼容形式、迁移调用方、清理旧形式分步，不强求每项都贯穿全部层。
- 默认在原需求的任务表维护；只有已有任务系统或确需独立跟进时拆出任务，原文用引用关联。
- 完成条件：每项有可验证结果，依赖无循环，当前可做项与受阻项可区分。
