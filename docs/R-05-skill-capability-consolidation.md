## 能力分组与14项映射

代码工作流统一采用 `code-` 前缀：`code-spec` 定义需求与验收，
`code-test` 证明行为并定位故障，`code-review` 检查实现与证据是否充分。
三者按需组合，不强制所有任务依次执行；`cn-writing` 与 `my-interview` 保留原名、独立补强。
14项范围保持稳定，合并只改变归属；后续若暂缓或移除某项，应在本表明确标注。

| 分组 | 原项 | 目标能力 | 实施方向 |
| --- | --- | --- | --- |

| 需求开发 | ④依赖提问、⑤业务术语、⑥行为拆分、⑩原型验证、⑪可追溯调研 | 澄清、设计和渐进实施 | `spec-coding` 升级为 `code-spec` |

## 验收标准

- **验收标准(AC-1)：文档写作**
  - 当引用条件性资料时，应说明读取条件、资料用途和入口；通用内容留在主文件。
  - 当流程步骤存在结束判断时，应使用可观察的完成条件。
  - 同一概念的定义、规则与例外集中维护；已有规则原位修正，避免重复追加。
- **验收标准(AC-2)：需求澄清**
  - 应先核实能从代码、配置或资料确认的事实，再向用户询问必要决策。
  - 需要多轮澄清时，问题按依赖提出并提供有依据的建议；已有结论不重复确认。
  - 业务术语有歧义或与代码行为冲突时，应展示具体场景和差异，再确定当前口径。
- **验收标准(AC-3)：任务、调研与原型**
  - 需要拆任务时，应围绕可独立展示或验证的行为划分，并标明真实阻塞关系。
  - 调研结论应关联一手来源，区分事实、推断与未确认项，沿用仓库资料入口。
  - 需要运行才能判断的问题，可使用原型验证；应写清问题、验证范围和结论。
    原型不默认升级为生产实现，不默认新增文档或发布流程。
- **验收标准(AC-4)：测试能力升级**
  - `code-test` 应覆盖前端、后端、接口与性能相关验证，并按行为、风险和成本选层。
  - 应通过公开行为验证结果，预期值来自规格或独立样例，不复制实现计算。
  - 适用 TDD 时按小步失败、实现、验证推进；已有代码和低影响改动按风险选取验证。
  - 应保留原 Spring 切片、集成、E2E 与基础设施经验，条件满足时才读取专项资料。
- **验收标准(AC-5)：故障诊断**
  - 当定位故障时，应先建立能识别该问题的复现或失败信号，再缩小范围并验证假设。
  - 修复后应复用原信号回归；无法稳定复现时，应说明证据、局限和下一步验证。
  - 业务故障保存在任务证据中，可复用的工具与环境故障按 `env-tool-log` 归位。
- **验收标准(AC-6)：审查与交付**
  - 应先固定审查范围，分别核对代码质量与需求符合度。
  - 发现应附具体位置、触发场景、影响和证据；缺少规格时应说明审查边界。
  - 交付或 PR 说明应按改动需要提供前后证据、影响范围及回退难度，不强制绘图。
- **验收标准(AC-7)：复盘与交接**
  - 当要求工程复盘时，`code-review` 应按需检查导航、规则、检查机制与工具效率；
    机械错误优先考虑确定性检查。
  - 长期改进应归入对应规则或工具，避免将所有经验追加到全局指令或错误日志。
  - 当要求代码任务交接时，应按可选参考保留目标、当前状态、未决事项、验证缺口和下一步；
    已有规格、提交与证据用路径或链接引用，并移除敏感信息。
  - 审查、复盘与交接应可分别调用，不因用户选择其中一项自动执行其余分支。
- **验收标准(AC-8)：面试学习**
  - 应按学习目标和已有证据安排练习，持久化薄弱点、掌握程度与复习计划。
  - 应通过回忆练习和实际表现调整进度，不以看过讲解代替掌握证据。
  - `my-interview` 保留原名及算法、八股、渐进提示和模拟面试能力；题库继续只读。
  - 面试学习与工程审阅独立触发，不将 `my-interview` 改造为通用学习教练。
  - 应复用已有学习档案；字段或路径变化时明确兼容方式，避免丢失历史记录。
- **验收标准(AC-9)：迁移与接入**
  - 技能改名时应核对正文、目录、UI 提示、跨技能引用、模板、示例和清单。
  - 新旧入口的迁移方式应明确，避免同名或近义技能重复加载；旧入口处理应可核验。
  - 发布时按仓库规则同步组件版本；本机安装更新另行执行，不手改插件缓存。
- **验收标准(AC-10)：连续审阅**
  - 应保留原14项的范围映射，按实际调用场景组织入口；已有等价规则优先复用。
  - 每轮只修改和展示本次涉及范围，不以技能数量减少作为收敛完成的依据。
  - 需求保持单份 MD，术语、研究和决策沿用既有入口，不强制额外建立文件。
  - 验证结果应标明实际范围；静态检查通过不等于真实客户端行为已验证。

## 关键设计

- **测试与审阅分工**：`code-test` 负责如何证明行为、如何定位故障；
  `code-review` 负责核对实现、需求和证据是否充分，避免重复维护测试方法。
  `code-spec` 管理需求、验收与证据映射，不重复维护具体测试和排障方法。
- **能力组合**：跨技能引用应说明触发条件；技能缺失时沿用项目已有约定并报告缺口。
  不依赖特定 harness 的工具名、hooks 或子 Agent 能力；并行仅在适用且获得授权时使用。
- **产物处理**：研究结论与已验证的原型决策回填已有任务文档；
  原型代码的清理、保留和提交遵循任务约定。
- **影响范围**：涉及技能目录、提示和安装清单，不改变博客发布 API、业务数据库或外部服务契约。

## 验证

### 行为验证场景

案例用于观察模型实际执行，实施时保留有代表性的输入和输出证据。
每组同时检查适用场景与相邻的不适用场景；仅检查规则文本或文件结构不算行为验证通过；下表的静态走查只确认相应分支与约束已写入，不代表模型已按案例执行。

| 场景 | 应观察的行为 | 对应验收标准 | 当前结果 |
| --- | --- | --- | --- |
| 编写 Agent 文档，存在通用规则与 Spring 专项细节 | 给专项引用明确触发条件，步骤有可检查的结束状态；人类短文不机械套用步骤格式 | AC-1 | 规则静态走查通过，实际执行待回归 |
| 用户提出上下文已清楚的小改动 | 自行核实事实并直接推进；不重新采访，也不强制调研、原型或拆任务 | AC-2~AC-3 | 规则静态走查通过，实际执行待回归 |
| 多个问题有前置依赖，且业务术语与代码冲突 | 先核实代码，用具体场景提出当前能决定的问题；已解决问题不重复确认 | AC-2 | 规则静态走查通过，实际执行待回归 |
| 需求需要调研和运行样例才能决定 | 引用一手来源，区分推断，明确原型回答的问题；按可验证行为拆任务并标记依赖 | AC-3 | 规则静态走查通过，实际执行待回归 |
| 分别处理 Spring 事务、前端交互、接口契约和性能问题 | 按风险选择足够真实且成本合理的验证；只读相关专项资料，预期值独立于实现 | AC-4 | 规则静态走查通过，实际执行待回归 |
| 用户报告偶发故障，尚无稳定复现 | 先构建复现或证据链，验证假设；修复后回归，未复现时不声称根因已证实 | AC-5 | 规则静态走查通过，实际执行待回归 |
| 用户只要求审查未提交改动，且没有规格文件 | 固定实际差异范围，区分代码质量和需求依据缺口；不顺带修改、提交或复盘 | AC-6~AC-7 | 规则静态走查通过，实际执行待回归 |
| 单独要求工程复盘，或单独要求代码任务跨会话交接 | 复盘把检查、规则和工具经验分别归位；交接保留状态与引用并脱敏，互不自动触发 | AC-7 | 规则静态走查通过，实际执行待回归 |
| 用户继续旧考点练习，随后进行算法或八股复习 | 复用已有档案，依据实际表现安排练习与复习；不误触发代码审阅，题库未被写入 | AC-8 | 规则静态走查通过，实际执行待回归 |
