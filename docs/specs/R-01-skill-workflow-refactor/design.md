# R-01 设计

## 文档模型

`spec-coding` 提供两种形态，不按固定行数机械切换：

### 紧凑模式

适用于目标单一、设计直接、验证结果简短的需求。一份 Markdown 包含状态、AC、关键决策、任务和
验证摘要。

### 目录模式

适用于跨组件、多阶段实施、存在独立架构说明，或验证记录会持续增长的需求：

```text
docs/specs/R-xx-name/
├── spec.md
├── design.md
└── verification.md
```

- `spec.md`：唯一状态源、范围、AC、关键决策、待确认项和验证映射。
- `design.md`：实现结构、权衡和影响范围，不重复 AC 与状态。
- `verification.md`：命令、结果、环境证据和遗留验证，不反向定义需求。
- `tasks.md` 仅在任务需要独立协作或长期跟踪时增加，不作为固定文件。

## Skill 边界

### spec-coding

负责需求生命周期、AC 和证据完整性，不决定 Spring 测试的具体写法。输出的验证映射至少包含：

| 字段 | 含义 |
| --- | --- |
| AC | 被证明的验收标准 |
| 风险/行为 | 为什么需要这一验证 |
| 验证层级 | 单测、切片、集成、E2E、人工或静态检查 |
| 用例/证据 | 测试位置、命令或报告链接 |
| 基线 | 改动前的失败、缺口或既有行为 |
| 当前结果 | 改动后的最新结果 |

### spring-testing

负责根据风险选择最低成本且足以证明行为的测试层级。若仓库已有 spec，则返回可回填验证映射的
层级、用例位置和外部依赖；不接管需求状态或文档结构。

## Spring 测试决策

- 纯计算和领域规则：纯单测。
- Spring MVC 映射、绑定、序列化：切片测试。
- SQL 方言、事务、Redis/Lua、消息协议、驱动行为：真实且隔离的基础设施。
- 跨进程部署行为：E2E。
- 配置中心只有在配置加载、隔离或热更新本身是目标时才使用真实服务。
- Testcontainers 无法表达集群、双 cell 或网络拓扑时，允许使用显式指定的隔离环境；禁止自动写入
  生产或共享业务数据。

## 渐进披露

- `SKILL.md` 保留决策规则和引用路由。
- WebMvc、Testcontainers、E2E、lbs-cloud 细节分别保留在 references 中，按任务读取。
- lbs-cloud 参考只保留框架级陷阱，不包含特定业务错误码、机器路径或环境地址。
